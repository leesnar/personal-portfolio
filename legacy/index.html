Project Overview

Background case

High-performing machine learning models like XGBoost are often black boxes. In clinical screening contexts, doctors and patients can’t act on a prediction they don’t understand — and Explainable AI tools like SHAP and LIME are frequently used without ever checking whether the explanation itself is stable, consistent, or medically plausible. This gap between “looks interpretable” and “is actually trustworthy” is what this research addresses.

Project Goals

To build and validate a multi-layer framework that audits SHAP and LIME explanations across three dimensions — computational stability, LLM-based semantic plausibility, and clinical domain-expert review — using heart disease classification as the test case.

My Role

AI/ML Engineer (Research)

My Responsibilities

Understand context of the problem

02

Main Problem

Explainable AI outputs (SHAP, LIME) are algorithmic artifacts that can be affected by data noise, method configuration, preprocessing, and model characteristics — so they cannot be accepted at face value. They need to be evaluated for stability, cross-method consistency, medical plausibility, and expert judgment.

Problem
“An accurate model with an untrustworthy explanation is not safe to deploy in healthcare — yet most XAI research stops at visualizing SHAP plots without testing whether that visualization is reliable.”
How to solve this problem?
03

Research

AU
Dr. dr. Amalia Tri Utami, M.Biomed
Biomedical Science Expert
Domain Validator
Background

Reviewed SHAP global/local plots, LIME local explanations, and SHAP–LIME overlap comparisons as the domain-expert layer of the validation framework.

Context

Existing XAI outputs are rarely tested for whether their reasoning aligns with actual clinical knowledge before being presented to healthcare stakeholders.

Needs

An explanation artifact that is readable, medically relevant, and honest about its own limitations — not just visually convincing.

Findings

Model performance trade-off: Random Forest led on accuracy (86.89%) and AUC-ROC (94.05%), but XGBoost was selected for recall (92.86%) — in screening, missing a sick patient is costlier than a false alarm.

Explanation stability varies by method: SHAP (TreeExplainer) is more deterministic since it reads the tree structure directly; LIME depends on local sampling and surrogate models, making it more sensitive to configuration.

Plausibility is feature-dependent: Features like thalach (75%) and cp (60%) aligned well with medical literature; features like chol (33%) needed caution due to phenomena like the cholesterol paradox.

Prospective Validation Journey

A prediction is generated → SHAP/LIME explanation is produced → explanation undergoes noise-based stability testing → direction of contribution is checked by GPT-4 against medical literature → final artifact is reviewed by a domain expert before being considered trustworthy.

Retrospective Validation Journey

Testing revealed that computational stability alone (Jaccard 0.72 for SHAP) wasn’t sufficient — semantic validation caught cases where a statistically stable explanation still lacked medical plausibility, which led to explicitly flagging “features requiring caution” (chol, ca) in the final framework.

Solution

A three-layer XAI validation framework: (1) computational stability testing via noise injection and Jaccard index, (2) LLM-based semantic validation of feature-contribution direction against medical literature, and (3) domain-expert review of the final artifacts — applied on top of a leakage-safe XGBoost/Random Forest pipeline.

Ideate & Methodology Design

05

Ideate

Computational Stability Testing

Inject Gaussian noise (σ=0.01) into 20 test patients across 30 iterations, then measure how much the top-5 SHAP/LIME feature set survives using the Jaccard index — revealing whether an explanation is a stable signal or noise-sensitive artifact.

LLM Semantic Validation Layer

Use GPT-4 as a literature-grounded reviewer (not a diagnostic tool) to score whether each feature’s direction of contribution — e.g. “higher age increases risk” — is medically plausible, producing a 1–5 alignment score per case.

Split first

Data is split before any transformation is fitted.

SMOTE in-fold

Resampling runs only on the training fold, never on validation data.

Split paths

Numeric and categorical features travel separate transformation paths.

Why the pipeline is built this way

Why split before any transformation: fitting an imputer or scaler on the full dataset lets test-set statistics leak into training, inflating every metric that follows.

Why SMOTE only in the training fold: synthesising minority samples across the whole set creates near-duplicates of validation rows, so the model is scored on data it has effectively seen.

Why numeric and categorical paths are separated: each type needs its own imputation and encoding strategy — KNNImputer + MinMaxScaler for numeric, SimpleImputer + One-Hot for categorical.

Conclusion

This research shows that evaluating a medical ML model requires more than accuracy — it requires layered scrutiny of the explanation itself: is it stable, is it consistent across methods, is it medically plausible, and does a domain expert agree. The project demonstrates both technical ML competency and the judgment to know when a result is “good enough to publish” versus “good enough to deploy” — two very different bars.

Project Overview

Background case

A security team receiving 47,700+ network connection logs per cycle can’t review them manually. Worse, a raw classifier that flags 46.6% of all traffic as anomalous produces alert fatigue — analysts start ignoring warnings, including real ones. The challenge wasn’t just detection; it was making detection operationally usable.

Project Goals

Build an end-to-end system that classifies network traffic as normal or anomalous, then translates that classification into a prioritized, actionable risk score — reducing the reviewable alert volume to a size a human team can realistically handle.

My Role

Data Analyst

My Responsibilities

Data Pipeline Engineering, Model Development, Risk Scoring System, Dashboard Engineering

Understand context of the problem

02

Main Problem

Without prioritization, security teams face a binary choice: investigate everything (impossible at scale) or investigate nothing systematically (dangerous). The system needs a middle layer that ranks urgency, not just detects anomalies.

Problem
“46.6% of traffic flagged as anomalous is not a usable security signal — it’s noise that overwhelms the team it’s meant to help.”
